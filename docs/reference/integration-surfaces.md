# Integration Surfaces for a Go-Orchestrated Multi-Agent Coding Harness (Herdr + Pi + Claude Code)
 
**TL;DR**
- All three surfaces support the design, but authority must be split deliberately: your Go CLI is the state authority; Herdr is UI/pane plumbing and a coordination bus (spawn, read, send-input, wait-on-state over a newline-delimited JSON local socket); Pi is your fully programmable GPT harness (RPC mode + in-process extensions); Claude Code is the least programmable of the three — drive it in interactive Herdr panes via screen-manifest detection plus its hook events, and reserve headless `-p`/`stream-json` for one-shot side tasks.
- The single most important finding for your design: a custom socket report via `pane.report_agent --source custom:*` **does become the pane's lifecycle authority and suppresses Herdr's built-in screen-manifest detection for that pane**, including for a recognized agent like Claude Code. This is a real override, not a coexistence — so if your Go relay reports custom state onto a Claude pane you must decide deliberately whether to let Herdr keep detecting Claude's blocked/working from screen, or to take over (and lose Herdr's built-in blocked detection). Use `pane.report_metadata` for display-only changes that do *not* seize authority, and `pane.clear_agent_authority`/`pane.release_agent` to hand authority back.
- The biggest operational landmine is Claude Code subscription limits: a 5-hour rolling window plus a weekly cap, pooled across *all* sessions and Claude chat on one account, and parallel subagent fan-out is the documented cause of premature exhaustion. Plan for ≤2–3 concurrent Claude panes, throttle fan-out, and treat rate-limit handling (StopFailure hook, backoff) as a first-class part of the orchestrator, not an afterthought.
## Key Findings
 
1. **Herdr's socket API is a complete orchestration surface**, not just a viewer. It exposes workspace/tab/pane/agent lifecycle over newline-delimited JSON on a Unix domain socket (named pipe on Windows), with `pane.split`, `pane.send_input`/`send_text`/`send_keys`, `pane.read`, `events.subscribe`, `events.wait`, and `agent.start`/`agent.send`/`agent.read`. It has a versioned protocol and an inspectable schema (`herdr api schema --json`). It is pre-1.0 (v0.7.1 line) and the maintainer is a solo developer, so treat the protocol as fast-moving.
2. **Herdr's authority model is the crux of your architecture.** Each pane has exactly one status authority. Claude Code is deliberately *not* a lifecycle authority in Herdr — its integration reports session identity only, and blocked/working come from screen-manifest detection. A custom socket state report overrides that. This is exactly the seam your zero-inference Go relay plugs into.
3. **Pi is the most programmable of the three surfaces.** It offers a JSONL RPC mode (`pi --mode rpc`), an in-process TypeScript SDK (`AgentSession`/`createAgentSessionRuntime`), a rich extension event bus (`before_agent_start`, `tool_call`, `agent_settled`, etc.), and — critically for you — it is a *lifecycle authority* in Herdr (its bundled extension reports idle/working/blocked, not just session identity). Pi is your GPT harness and the one agent whose state Herdr can track natively and accurately.
4. **Claude Code is driveable but constrained.** Programmatic control is via hooks (30+ events incl. Stop, Notification, PreToolUse, PermissionRequest), headless `-p` with `--output-format json|stream-json`, and session resume by ID. But interactive-mode input injection is unreliable (the Ink TUI does not treat programmatic `\r` as submit), so in visible Herdr panes you drive it via `pane.send_text`+`send_keys` (Enter as a separate keypress). Subscription rate limits are pooled and parallel-hostile.
5. **Prior art converges on a consistent pattern**: git-worktree isolation per worker, non-overlapping file ownership declared up front, a planner/architect stage, a dedicated reviewer stage, an out-of-process coordinator holding the loop and enforcing one-writer-per-namespace via a file lock, and durable state in SQLite or an event-sourced log. Your design matches this; the Go ecosystem has mature building blocks (`gofrs/flock`, `looplab/fsm`, `cschleiden/go-workflows`, `microsoft/durabletask-go`).

## Workstream 1 — Herdr Socket API: Pane/Agent Lifecycle and Custom State Authority
 
**Transport & discovery.** Herdr uses newline-delimited JSON, one request per line, over a Unix domain socket (named pipe on Windows). Socket resolution order: explicit CLI `--session <name>` › `HERDR_SOCKET_PATH` › `HERDR_SESSION=<name>` › default session socket. Default socket lives under the Herdr config dir; named sessions get their own socket under `sessions/<name>/herdr.sock`. Herdr injects `HERDR_SOCKET_PATH`, `HERDR_ENV=1`, `HERDR_WORKSPACE_ID`, `HERDR_TAB_ID`, and `HERDR_PANE_ID` into every managed pane process; Herdr-managed vars are authoritative over caller-provided env. (Source: herdr.dev/docs/socket-api, 2026-07-17.)
 
**Bootstrapping.** `session.snapshot` (CLI `herdr api snapshot`) returns a one-time bootstrap: version/protocol metadata, focused workspace/tab/pane ids, and workspace/tab/pane/agent records plus layout snapshots. The documented pattern is: read `session.snapshot` once, then subscribe to resource events and update a local cache from those events; re-snapshot on reconnect. This maps cleanly onto a Go relay that keeps an in-memory mirror but treats its own store as truth.
 
**Full method surface (raw dot-notation).** Server: `ping`, `server.stop`, `server.reload_config`, `server.agent_manifests`, `server.reload_agent_manifests`. Session: `session.snapshot`. Workspace/Tab: create/list/get/focus/rename/move/close (+ `workspace.report_metadata`). Pane: `pane.split`, `pane.swap`, `pane.move`, `pane.zoom`, `pane.layout`, `pane.process_info`, `pane.list/current/get/rename`, `pane.send_text`, `pane.send_keys`, `pane.send_input`, `pane.read`, `pane.report_agent`, `pane.report_agent_session`, `pane.report_metadata`, `pane.clear_agent_authority`, `pane.release_agent`, `pane.close`, `pane.wait_for_output`, plus experimental `pane.graphics.*`. Agent: `agent.list/get/read/explain/send/rename/focus/start`. Events: `events.subscribe`, `events.wait`. Integrations: `integration.install/uninstall`. (Source: herdr.dev/docs/socket-api, 2026-07-17.)
 
**Lifecycle primitives you'll use:**
- **Spawn**: `agent.start reviewer --cwd ~/proj --split right -- pi` (treats a pane as an agent target that shows in `agent list`, can be waited on, read, sent input, attached). Use `pane.split`+`pane.run` for non-agent terminals (tests, servers). `layout.apply` can build a whole tab tree declaratively with labels, cwd, env, and argv commands (but does *not* preserve live PTYs/scrollback — it's for structure, not live restore).
- **Read output**: `pane.read --source visible|recent|recent-unwrapped|detection`. `recent-unwrapped` ignores soft wrapping (best for logs); `detection` returns the exact bottom-buffer snapshot used by screen detection.
- **Send input**: `pane.send_input` sends text + encoded keypresses in one request (with bracketed-paste handling); use it when you need "text + real Enter." `send_keys` accepts key-combo strings (`enter`, `esc`, `ctrl+h`, `shift+tab`, `f1`, `minus`). It does *not* accept `prefix+` binding strings.
- **Wait-on-state**: `herdr wait agent-status <pane> --status done|blocked` is a CLI convenience over an `events.subscribe` on `pane.agent_status_changed`. `herdr wait output --match <re>` waits on recent terminal text. Waits observe *semantic* state, not arbitrary command completion.
- **Events**: pane events include `pane.created/updated/closed/focused/moved/exited/agent_detected/output_matched/agent_status_changed/scroll_changed`; also workspace, tab, worktree, and `layout.updated` events. Subscriptions keep the connection open after the first ack.
**Custom state reporting vs. built-in detection (the pivotal question).** Herdr assigns each pane exactly one status authority. Verbatim: *"Herdr first detects the foreground process in each pane. After that, each pane has one status authority."* (herdr.dev/docs/agents, 2026-07-17.) For a full-lifecycle authority, *"It does not also run screen manifest fallback for that same lifecycle authority. This avoids two competing sources of truth."* (same page.)
 
A custom socket report **overrides** screen-manifest detection. When you call `pane.report_agent` with `source: "custom:*"` and a semantic `state`, that source becomes the pane's lifecycle authority and suppresses screen rules — the same mechanism a built-in lifecycle hook uses. Herdr's bundled `SOCKET_API.md` states of `pane.report_agent`: *"while this authority is active, the reported `agent` and `state` override heuristic display for that pane"* and *"process detection still owns pane liveness and fallback when hook authority is cleared or released."* (SOCKET_API.md, preserved in fork mirror re2zero/herdrzero, fetched 2026-07-17 — flagged because this prose is not in the current herdr.dev/docs/socket-api page.)
 
**This directly answers your question about Claude Code.** Claude Code is *"intentionally not [a] lifecycle authorit[y]"* — its hook reports session identity, and state comes from screen manifest (herdr.dev/docs/agents). So on a Claude pane there is normally no lifecycle authority; screen detection owns blocked/working. If your Go relay then calls `pane.report_agent --source custom:...` with a state, **the custom source seizes authority and suppresses Claude's screen-manifest blocked/working detection**. That is a genuine conflict/override, and it is a design decision, not an accident:
- If you want Herdr's built-in Claude blocked detection (e.g., permission prompts show as `blocked` in the sidebar) to keep working, do **not** report semantic state onto Claude panes — use `pane.report_metadata` (display-only: title, `display_agent`, `state_labels`, tokens) which explicitly does *not* take over lifecycle state.
- If you want your orchestrator's notion of state to drive the sidebar/waits (because your Go CLI is the state authority), report it via `pane.report_agent --source custom:...` and accept that you now own state for that pane.
- Confirm which is active with `herdr agent explain <pane> --json`: it reports `screen_detection_skip_reason` when a lifecycle authority makes screen rules non-authoritative.
**Giving authority back.** `pane.clear_agent_authority {pane_id, source?}` clears hook authority for a pane; with `source` omitted it clears *any* authority, with `source` present it clears only that source, and fallback detection resumes. `pane.release_agent {pane_id, source, agent}` is a *clean-exit* signal: it drops the pane's agent identity immediately (back to shell) instead of waiting for fallback, and for built-in agents applies a short "reacquire suppression" window. (SOCKET_API.md fork mirror, 2026-07-17; both methods are listed but unexplained in the live docs.)
 
**Sequence/ordering and re-anchoring.** `pane.report_agent` accepts an optional `seq`. Rule (verbatim, herdr.dev/docs/socket-api): *"For the same `source`, reports with a sequence number less than or equal to the last accepted sequence are accepted by the API but ignored by the pane state."* So use a monotonic counter per source. A documented 32-distinct-source lifetime cap exists explicitly for sequenced *token/metadata* reports (*"A pane or workspace accepts sequenced token reports from at most 32 distinct sources during its lifetime; clearing or expiry does not release those source slots"*); whether the identical cap applies to `report_agent` state reports is **not explicitly documented** — treat it as an unknown and keep your source identifiers few and stable. After a proven process exit or a fresh session reference, Herdr re-anchors sequence guards (CHANGELOG #684: *"Herdr keeps process-exit validation active under lifecycle authority and re-anchors hook sequence guards after fresh session references or proven process exits"*).
 
**Protocol versioning & stability.** Herdr *"has a protocol version for client/server compatibility"* and advises checking the server protocol via `ping` or `herdr status` before depending on new behavior and to *"Handle unknown fields gracefully."* `agent.explain` availability depends on a server new enough to support it — *"after upgrading Herdr, restart or live-handoff the server before relying on this method."* The project is pre-1.0 (v0.7.1 line as of mid-2026), AGPL-3.0, and a solo project with a strict contribution policy, so breaking changes are plausible between minor releases. The socket schema is self-describing (`herdr api schema --json`) — generate your Go types from it and re-generate on upgrade.
 
**Integration contract — Herdr.**
- *APIs*: newline-delimited JSON over Unix socket; methods listed above; `session.snapshot` + `events.subscribe` for a cached mirror; `herdr api schema --json` for the schema.
- *Invocation examples*: `herdr agent start impl-1 --cwd ~/proj --split right -- pi`; `herdr pane read w1:p2 --source recent-unwrapped --lines 120`; `herdr wait agent-status w1:p1 --status blocked`; `herdr pane report-agent w1:p1 --source custom:relay --agent impl-1 --state working --seq 42`; `herdr pane report-metadata w1:p1 --source user:title --token summary=refactor`.
- *Version/stability caveats*: pre-1.0, solo-maintained, protocol-versioned; `pane.clear_agent_authority`/`pane.release_agent` semantics only in bundled `SOCKET_API.md`, not live docs; the 32-source cap's applicability to state reports is undocumented; verify with `agent explain --json`; regenerate Go types from schema on every upgrade.

## Workstream 2 — Pi as a Programmatically Driven GPT Harness
 
**Architecture.** Pi (earendil-works/pi, published as `@mariozechner/pi-*` / `@earendil-works/pi-*`) is a layered TypeScript monorepo: `pi-ai` (unified multi-provider LLM API: OpenAI, Anthropic, Google, Copilot…), `pi-agent-core` (agent loop, tool calling, events), `pi-coding-agent` (the coding CLI, sessions, extensibility), `pi-tui` (terminal UI). It ships only a small core of built-in tools; everything else is an extension. There is no built-in permission sandbox — it runs with the launching user's permissions (containerize if you need boundaries). It supports subscription logins (Claude Pro/Max, ChatGPT Plus/Pro via Codex, GitHub Copilot) *and* API-key providers — so Pi can be your GPT/OpenAI harness via `/login` or env keys.
 
**Three ways to drive it programmatically:**
1. **RPC mode** (`pi --mode rpc`): strict JSONL over stdin/stdout (LF-only framing — do *not* use Node `readline`, which splits on U+2028/U+2029). Commands include `prompt` (with `streamingBehavior: "steer"|"followUp"` while streaming), `steer`, `follow_up`, `abort`, `new_session`, `switch_session`, `fork`, `clone`, `get_state`, `get_messages`, `get_entries` (append-only cursor via `since` — durable across restarts), `set_model`, `set_thinking_level`, `compact`, `set_auto_compaction`, `set_auto_retry`, `bash`. Events stream to stdout: `agent_start`, `agent_end` (with `willRetry`), `agent_settled` (fully settled — no retry/compaction/queued continuation left), `turn_start/end`, `message_*`, `tool_execution_*`, `queue_update`, `compaction_*`, `auto_retry_*`, `extension_error`. There's also an extension-UI request/response sub-protocol (`select`, `confirm`, `input`, `editor`, `notify`, `setStatus`) — dialog methods block awaiting an `extension_ui_response`.
2. **In-process SDK** (`@earendil-works/pi-coding-agent`): `AgentSession` / `createAgentSessionRuntime()` — the same layer used by interactive, print, and RPC modes. Preferred over subprocess for a Node/TS host, but your orchestrator is Go, so RPC-over-subprocess (or running Pi in a visible Herdr pane) is the natural path.
3. **Extensions** (in-process TS modules, auto-discovered from `~/.pi/agent/extensions/` and `.pi/extensions/`): they receive Pi's `ExtensionAPI` and can register tools, register commands, rewrite context, change compaction, and redraw UI — a strictly larger surface than Claude Code hooks. Event bus (from extensions.md): `project_trust`, `session_start`, `resources_discover`, `input`, `before_agent_start` (inject message / modify system prompt), `agent_start`, `turn_start`, `context` (modify messages non-destructively), `before_provider_headers`, `before_provider_request`, `after_provider_response`, `tool_execution_start`, `tool_call` (can block), `tool_execution_update`, `tool_result` (can modify), `tool_execution_end`, `turn_end`, `agent_end`, `agent_settled`. `ctx.sendUserMessage`/`sendMessage` with `deliverAs: "steer"|"followUp"|"nextTurn"` and `triggerTurn` let an extension inject work.
**How authoritative is Pi's Herdr lifecycle integration?** Strongly authoritative and native. `herdr integration install pi` writes `~/.pi/agent/extensions/herdr-agent-state.ts` (honoring `PI_CODING_AGENT_DIR`). Per herdr.dev/docs/agents, Pi's state authority is *"lifecycle hooks when installed; otherwise screen manifest"* and its integration role is *"state and session"* — i.e., when installed Pi authoritatively reports idle/working/blocked *and* a native session reference for restore. This is the key asymmetry with Claude Code: Herdr can track Pi's real lifecycle accurately, so your reviewer/implementer *Pi* dyads get precise blocked/working/done in the sidebar and via `wait agent-status` without you reporting custom state. Recent changelog entries (#943/#1189) show active hardening: *"Pi lifecycle state now reanchors after native session replacement, avoiding working panes that remain idle or tied to an abandoned session,"* and Pi state socket reports are now retried on startup races (#1049) — evidence the integration is maintained but still stabilizing.
 
**Integration contract — Pi.**
- *APIs*: `pi --mode rpc` (JSONL, LF-framed); `AgentSession` SDK; extension event bus + `registerTool`/`registerCommand`/`sendUserMessage`; session flags `-c`/`--session`/`--fork`/`--name`/`--no-session`.
- *Invocation examples*: `herdr agent start impl-gpt --cwd ~/proj --split right -- pi --mode rpc --provider openai --model gpt-5.6`; RPC `{"id":"1","type":"prompt","message":"implement X"}`; wait for `{"type":"agent_settled"}`; steer with `{"type":"steer","message":"also update tests"}`.
- *Version/stability caveats*: RPC LF-only framing (readline pitfall); no built-in permission sandbox; extensions run arbitrary code with full user perms; `save-exact`/`min-release-age` in the repo signals dependency caution; Herdr Pi integration version 2 required for native restore; lifecycle reanchor bugs were recently fixed, so pin/verify versions.

## Workstream 3 — Claude Code Programmatic Control
 
**Hooks.** Claude Code exposes a large hook lifecycle (documented as 30+ / "32" events depending on source; the first six cover most usage). Events relevant to orchestration: `PreToolUse` (gate/rewrite tool input; exit code 2 blocks deterministically; `hookSpecificOutput.permissionDecision`), `PermissionRequest` (pre-empt the permission dialog; `addPermissionRuleOnAllow`), `PermissionDenied` (`retry: true`), `PostToolUse`/`PostToolUseFailure` (react/rewrite results), `Stop`/`SubagentStop` (fire on completion; can force continuation — the Ralph-loop primitive; prompt-type Stop hooks allow LLM evaluation of "should stop"), `Notification` (permission_prompt / idle_prompt / auth_success — the "needs input" signal), `SessionStart` (startup/resume/clear/compact; stdout injected as context), `SessionEnd`, `UserPromptSubmit`, `PreCompact`, and a `StopFailure` matcher on `rate_limit`. Command hooks receive JSON on stdin (incl. `session_id`, `cwd`, `transcript_path`); HTTP hooks receive it as POST body; `async: true` (since Jan 2026) runs non-blocking. In the Agent SDK the same events are in-process callbacks on `options.hooks`.
 
**Herdr uses exactly one of these.** `herdr integration install claude` writes `~/.claude/hooks/herdr-agent-state.sh` (honoring `CLAUDE_CONFIG_DIR`) and adds hook entries to `settings.json`. Per DeepWiki, the hook is a shell script invoking an embedded Python one-liner that reads the event JSON, extracts the session id, and sends a `pane.report_agent_session` to Herdr — session identity only, with SubagentStop specifically prevented from reverting pane idle state. So Claude's blocked/working in Herdr always comes from screen-manifest detection, never its hooks. (This is why the Workstream-1 override matters.)
 
**Headless vs. interactive.** `claude -p "<prompt>"` runs the full agent loop non-interactively and exits; `--output-format text|json|stream-json` (stream-json requires `--verbose`; token deltas need `--include-partial-messages`). `--input-format stream-json` enables bidirectional streaming of user messages into one process. Two-stage session threading: capture `session_id` from the first run's JSON, then `claude -p --resume "$session_id" "<next>"`. `--session-id <uuid>` sets the id on the first run; `--resume <id>` for every run after; `--continue`/`-c` resumes the most recent session *in the current cwd*. Guardrails: `--max-turns` (print-mode only; exits with error at the limit), `--allowedTools`, `--permission-mode default|acceptEdits|plan|dontAsk|bypassPermissions`, `--bare` (ignore local hooks/MCP/CLAUDE.md for deterministic CI). Sessions are stored per-project under `~/.claude/projects/<cwd-hash>/` — **resume must run from the same cwd**, and in `-p` mode `--continue` may occasionally spawn a new session, so always resume by explicit id.
 
**Interactive input injection caveat.** Because your design runs Claude in visible, interactable Herdr panes (not headless), note that Claude Code's Ink TUI does *not* treat programmatically-sent `\r`/`\n` as submit (issue #15553). To drive an interactive Claude pane from the Go relay you must send the prompt text then a *real* Enter keypress — i.e., `pane.send_input {text, keys:["enter"]}` — and, for the `--dangerously-skip-permissions` warning, send `Down` then `Enter`. This is the tmux `send-keys` pattern lifted onto Herdr's socket. Permission modes matter here: `acceptEdits` auto-approves file edits but still gates bash; `plan` proposes without executing; `bypassPermissions` is refused under root/sudo and offers no prompt-injection protection. Claude Code v2.1.200+ also blocks, by default, an agent sending keystrokes to its own tmux/pane to change its own permissions — relevant if your relay's input could be misread as self-modification.
 
**Subscription rate limits under parallel sessions.** This is the sharpest operational constraint. On Pro/Max, Claude Code shares a **5-hour rolling window** (opens on first prompt, resets 5h later) **plus a weekly cap** (resets at an account-assigned fixed time, not Monday), and usage is **pooled across all Claude Code sessions and Claude chat on the same account** — per Anthropic's Claude Code subscription note (summarized by truefoundry.com, 2026): *"The same bucket is shared across Claude Code, Claude.ai chat, and Cowork — burn tokens in one, you lose capacity in the others."* Anthropic publishes only relative multipliers, not token quotas — per Anthropic's own material (as documented by ccforeveryone.com, June 2026): *"One thing Anthropic does not publish: exact token quotas for any plan. The official material gives multipliers only (Pro 1x, Max 5x or 20x)"* (Max 5x = $100/mo, Max 20x = $200/mo). On May 6, 2026, Anthropic doubled the 5-hour limits and removed peak-hour throttling; per Anthropic's news post *"Higher usage limits for Claude and a compute deal with SpaceX"* (anthropic.com/news, May 6 2026): *"First, we're doubling Claude Code's five-hour rate limits for Pro, Max, Team, and seat-based Enterprise plans. Second, we're removing the peak hours limit reduction on Claude Code for Pro and Max accounts."* Weekly caps were not mentioned and are unchanged.
 
The documented failure mode for parallel work is subagent fan-out: *"When Claude Code fans out subagents through the Task tool, each subagent is a separate stream of requests, and each one carries its own copy of the context as input tokens"* — and a known issue documents 5–10 parallel sessions launching subagent fan-outs and hard-failing under capacity errors (ofox.ai, 2026). Anthropic itself reset limits after *"an issue that caused some Claude Code sessions to spawn excessive parallel subagents"* (ClaudeDevs, X). Mitigations: `CLAUDE_CODE_MAX_TOOL_USE_CONCURRENCY` to cap fan-out, prompt caching (cache-read tokens generally don't count against ITPM), and a `StopFailure`/`rate_limit` hook to detect and queue-for-reset. Note also: from June 15, 2026, non-interactive usage (Agent SDK, `claude -p`, GitHub Actions) draws from a *separate* monthly credit on subscriptions — per morphllm.com/claude-code-usage-limits (citing an Anthropic Help Center notice): *"a separate monthly credit: $20 on Pro, $100 on Max 5x, $200 on Max 20x,"* billed at API list rates, and *"Credit does not roll over."* (One source reports this change was later paused; treat the exact billing boundary as fast-moving and verify against Anthropic's own docs before relying on it.)
 
**Integration contract — Claude Code.**
- *APIs*: settings.json hooks (30+ events) / Agent SDK callbacks; `claude -p` + `--output-format json|stream-json`; `--session-id`/`--resume`/`--continue`; permission modes/allowedTools; Herdr integration = session identity only.
- *Invocation examples*: interactive pane `herdr agent start reviewer --cwd ~/proj -- claude --permission-mode plan`; drive via `pane.send_input {pane_id, text:"review PR", keys:["enter"]}`; headless side task `sid=$(claude -p "start review" --output-format json | jq -r .session_id); claude -p --resume "$sid" "now write tests"`.
- *Version/stability caveats*: interactive submit needs real Enter keypress (Ink limitation); resume tied to cwd; `-p --continue` may fork a new session; no published exit-code table (branch on zero/non-zero); rate limits pooled and parallel-hostile; self-permission-change guard in v2.1.200+; subscription billing boundary (June 15, 2026) in flux.

## Workstream 4 — Prior Art and Go Building Blocks
 
**How existing Claude Code orchestrators implement the patterns you want:**
- **Planner/reviewer loops with consensus**: `nwiizo/ccswarm` (Rust) runs a `plan → Sangha consensus → implement → review → fix` pipeline defined in flow YAML, with per-stage provider selection (claude/codex/copilot), a `readonly` reviewer permission, a quorum-based multi-persona review stage (planner/reviewer/qa), and rate-limit-aware provider fallback (`on_rate_limit.provider`). It demonstrates provider-agnostic session bridging with retry/context/persistence.
- **Ralph-loop verifier chains**: Antfarm (Ryan Carson) over OpenClaw runs planner/dev/verifier/tester/reviewer roles, each story in its own worktree, coordinated via YAML + cron + SQLite — a concrete template for durable, overnight, deterministically-verified runs.
- **Native Claude Code coordination**: `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` (v2.1.32+) adds a shared task list with dependencies, mailbox messaging between agents, and **file locking to prevent conflicts** — the closest first-party analog to your design, but experimental, one-team-per-session, with no session resumption and lagging task status. Rate limits remain the real parallelism ceiling ("pooled across all sessions on your account").
- **File-lock coordinators**: A widely-cited practitioner pattern (dev.to/javatarz) is *"an out-of-process coordinator that holds the cycle loop, enforces one-agent-per-project-namespace at a time via a file lock, and writes a structured handoff that the next agent reads cold rather than inheriting from a long conversation"* — precisely your zero-inference Go relay. `Forge Orchestrator` (Rust, ~3MB) adds file locking + knowledge capture + drift detection across Claude Code/Codex/Gemini on one repo.
- **Worktree isolation as the universal substrate**: Every tier-2 orchestrator (Conductor, Vibe Kanban, Claude Squad, Antigravity, Cursor background agents) gives each worker its own git worktree + branch, shares one object store, and merges one branch at a time in dependency order. The documented hazard is `.git/index.lock` contention and silent operation on stale data when agents share a checkout — which is why file ownership must be declared up front and shared files (lockfiles, migrations, root config, shared interfaces) must be sequenced, never parallelized. Claude Code has native worktree support (`claude --worktree <name>`, `.claude/worktrees/`) since v2.1.49.

## Architecture Fit — Mapping onto Your Design
 
**The authority split.** Your stated invariant (the Go CLI is the state authority; Herdr is UI/pane plumbing) is directly supported and is the right call. Concretely:
- **Pi dyads**: let Herdr's native Pi lifecycle authority report idle/working/blocked. Your Go relay *reads* this (via `events.subscribe` on `pane.agent_status_changed` or `wait agent-status`) as an *input signal*, but your SQLite store remains truth. No custom `report_agent` needed for Pi — you get accurate state for free.
- **Claude panes**: Claude has no lifecycle authority in Herdr, so screen-manifest gives you `blocked` when a permission/approval prompt is visible — genuinely useful for human-escalation routing. **Recommendation: keep screen detection for Claude and do *not* seize authority with `report_agent`.** Instead, use `pane.report_metadata` (display-only) to surface your orchestrator's role labels/summary tokens in the sidebar. Reserve `pane.report_agent --source custom:*` for panes running agents Herdr can't detect at all, or where you deliberately want your state machine to drive the sidebar. If you ever do seize authority, remember to `pane.clear_agent_authority --source custom:...` (or `pane.release_agent` on clean exit) to restore built-in detection.
**Planner + adversarial-reviewer loop.** Model as a `looplab/fsm` (or `go-workflows`) state machine per task: `planning(planner Pi) → plan_review(adversarial reviewer, readonly) → [approve|revise] → implementing → impl_review → [merge|rework]`. The reviewer runs in its own visible pane (Pi RPC or Claude in `--permission-mode plan`). Drive transitions off Herdr `agent_settled`/`agent-status done` events for Pi, and off Claude's `Stop`/`Notification` hooks (routed through your Go relay's hook-callback endpoint — command hooks can be a tiny shell one-liner that POSTs the event JSON to your relay, mirroring how Herdr's own Claude hook works). Human escalation = a Herdr `blocked` rollup + `notification.show` to the operator.
 
**Parallel implementer + reviewer dyads with file locking.** One git worktree per implementer (via `worktree.create` — it returns workspace/tab/root_pane/worktree records and emits lifecycle events). Declare non-overlapping file ownership in your SQLite store before dispatch; enforce one-writer-per-namespace with `gofrs/flock` on a per-namespace lockfile (belt-and-suspenders atop worktree isolation, matching the practitioner coordinator pattern). Sequence any task touching shared files (lockfiles, migrations, root config, shared interfaces). Merge one branch at a time in dependency order.

## Recommendations (staged)
 
**Stage 0 — De-risk the two hard unknowns with experiments (before writing the relay).**
1. *Authority-override experiment*: run Claude in a Herdr pane, trigger a permission prompt, confirm sidebar shows `blocked` via screen manifest; then call `pane.report_agent --source custom:test --state working` and re-check with `herdr agent explain --json` for `screen_detection_skip_reason`. Then `pane.clear_agent_authority --source custom:test` and confirm screen detection resumes. This validates the pivotal behavior on *your* Herdr version. **Threshold to change plan**: if override does not suppress screen detection as documented, you can safely dual-report; if it does (expected), adopt the "metadata-only for Claude" rule.
2. *Interactive Claude input experiment*: confirm `pane.send_input {text, keys:["enter"]}` submits a prompt to an interactive Claude pane and that the `--dangerously-skip-permissions`/trust dialogs need `Down`+`Enter`. **Threshold**: if reliable, drive Claude interactively; if flaky, fall back to `-p`/`stream-json` for Claude workers and reserve panes for visibility only.
3. *Rate-limit experiment*: run 2, then 3, then 4 concurrent Claude panes on your actual Max plan doing representative work; measure time-to-first-429/weekly-cap warning; wire a `StopFailure`/`rate_limit` hook. **Threshold**: set your max concurrent Claude panes to one below where you first hit sustained throttling.
**Stage 1 — Build the relay core.** Go CLI with: a `gofrs/flock` namespace-lock module; a SQLite event log + task/ownership tables; a Herdr socket client with Go types generated from `herdr api schema --json`; `session.snapshot`+`events.subscribe` mirror; an HTTP endpoint that Claude command hooks POST to; a Pi RPC subprocess manager (LF-framed). Start with `looplab/fsm` for routing; graduate to `go-workflows` only if you need replay/durable-timer semantics.
 
**Stage 2 — Planner + adversarial reviewer, single task, no parallelism.** Prove the loop end-to-end with one Pi planner + one Pi (or Claude-plan-mode) reviewer, human escalation via `notification.show` + `blocked` rollup.
 
**Stage 3 — Parallel implementer/reviewer dyads.** Add `worktree.create` per implementer, file-ownership enforcement, one-branch-at-a-time merge. Cap Claude concurrency per Stage-0 finding.
 
**Stage 4 — Hardening.** Protocol-version pinning + schema regeneration on Herdr upgrade; retry/backoff on Herdr socket and Pi RPC; StopFailure-driven queue-for-reset on Claude; chaos-test Herdr server restart to confirm your SQLite log fully reconstructs orchestration state.
 
**Model/role routing (from prior art):** planning → a cheaper/reasoning model; implementation → Sonnet/GPT-5.6/Opus; review → a dedicated reviewer model. Keep any `AGENTS.md`/`CLAUDE.md` human-authored: an ETH Zurich study ("Evaluating AGENTS.md", Feb 2026, cited by Addy Osmani) found *"LLM-generated context files reduced task success by 2–3% while increasing cost by over 20%. Developer-written files improved success by about 4%."*
 
## Caveats
 
- **Pre-1.0, fast-moving surfaces.** Herdr is v0.7.x, solo-maintained, AGPL-3.0, protocol-versioned; expect breaking changes. Pi and Claude Code both ship changes weekly. Every version-specific detail here (method names, hook events, rate-limit numbers, billing boundaries) should be re-verified against primary docs at build time.
- **Undocumented Herdr behavior.** `pane.clear_agent_authority` and `pane.release_agent` semantics are documented only in Herdr's bundled `SOCKET_API.md` (sourced here via a fork mirror), not the live docs — verify against your binary's `herdr api schema --json`. Whether the 32-distinct-source lifetime cap applies to `report_agent` (vs. only token reports) is undocumented. The exact arbitration when a custom source *and* a native session hook both report on one Claude pane is not spelled out beyond "one authority per pane."
- **Claude subscription limits are the primary scaling risk** and are deliberately unpublished as absolute numbers; the May 6 2026 doubling and June 15 2026 SDK-credit change show how quickly the billing model shifts. Do not architect around a specific token quota.
- **Claude interactive input is a known rough edge** (Ink submit behavior, issue #15553) and Anthropic's v2.1.200+ self-permission-change guard could interfere with aggressive input injection — hence the Stage-0 experiment.
- **Some sourcing is secondary.** Rate-limit specifics and prior-art orchestrator details come from independent blogs/practitioner posts (labeled inline); the authority-model and API specifics come from primary Herdr/Pi/Anthropic docs. Where a claim is vendor-stated vs. independently verified, that distinction is noted in-text.
- **Out of scope, as requested**: knowledge-base/architecture-doc storage design, model-quality comparisons, and non-Herdr UIs are not covered.
